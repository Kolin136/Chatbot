# `app/llm.py` 코드 해석

## 파일 역할

챗봇의 **두뇌** 역할. 사용자 질문과 RAG가 찾아온 참고 문서를 받아서 **Gemini LLM에게 답변을 만들어달라고 요청**하는 모듈.

이 파일이 담당하는 것 4가지:
1. **시스템 프롬프트 정의** — LLM에게 "너는 Jarana의 CS 에이전트다"라고 역할 지시
2. **PydanticAI Agent 싱글톤 생성** — LLM과 통신할 객체 한 번만 만들어놓고 재사용
3. **세션별 대화 히스토리 저장** — 같은 세션 ID의 이전 대화를 기억해서 문맥 유지
4. **프롬프트 조립 & LLM 호출** — RAG 컨텍스트 + 사용자 질문을 합쳐서 Gemini에게 전달

`routers/chat.py`가 이 파일의 `generate_response()`를 호출하고, 이 파일은 `config.py`의 `GEMINI_MODEL`을 사용한다. 실질적으로 **챗봇의 동작 중심**이 여기에 있다.

### 핵심 개념: "LLM 호출의 전체 구조"

LLM을 호출한다는 건 그냥 "질문 보내고 답변 받기"가 아니다. 실제로는 **3가지 요소를 조합해서** API 요청을 보내는 과정:

1. **시스템 프롬프트** (System Prompt) — LLM의 역할과 규칙을 정의. 대화 내내 고정.
2. **메시지 히스토리** (Message History) — 지금까지의 사용자/AI 대화 기록. 문맥 유지용.
3. **현재 사용자 메시지** (User Message) — 방금 들어온 새 질문.

LLM API는 이 3가지를 하나의 **대화 배열**로 받아서 "다음에 AI가 뭐라고 말할지"를 예측한다. 이 파일은 이 3가지 요소를 조립해서 PydanticAI Agent에게 넘기는 역할을 한다.

### `"""\` 시작 부분의 백슬래시 의미

파이썬의 삼중 따옴표 문자열은 그대로 쓰면 첫 줄에 `\n`(줄바꿈)이 들어간다. 맨 앞에 `\`를 붙이면 **첫 줄의 줄바꿈을 제거**해준다. 그래서 실제 문자열은 `"당신은 ..."`으로 깔끔하게 시작한다.

```python
# 이렇게 쓰면 ↓
x = """\
hello"""
# 결과: "hello"  (줄바꿈 없이 바로 시작)

# 이렇게 쓰면 ↓
y = """
hello"""
# 결과: "\nhello"  (맨 앞에 줄바꿈 포함)
```

### 시스템 프롬프트란?

LLM API 호출 시 **역할과 규칙을 지정하는 최상위 지시문**. 일반적인 LLM API에서 메시지는 3가지 role을 가진다:

| role | 의미 | 예시 |
|------|------|------|
| `system` | 규칙/역할 지정 (항상 최상단) | "너는 CS 에이전트다. 마크다운 금지." |
| `user` | 사용자가 입력한 질문 | "발음 점수는 어떻게 매겨지나요?" |
| `assistant` | LLM이 생성한 답변 | "발음 점수는 정확도, 유창성..." |

**system 메시지는 매 대화에서 한 번만 정의하고, 이후 모든 요청에 자동으로 포함된다.** 그래서 "너는 무엇이다"는 규칙을 대화 내내 유지할 수 있다.

### 이 프롬프트가 LLM에게 지시하는 것 4가지

1. **역할 정의**: "Jarana의 CS 에이전트"
2. **컨텍스트 기반 답변 강제**: `[참고 문서]`에 있는 내용만 근거로 쓸 것 (= RAG의 환각 방지)
3. **모르는 건 "확인 후 안내" 라고 답할 것**: 거짓말 방지
4. **마크다운 금지**: 프론트엔드가 마크다운 렌더링을 안 하기 때문에 `**`나 `##` 같은 문법이 그대로 보이면 이상해 보임 → 강제로 막음

## Line 42-44: 히스토리 프로세서 함수

```python
async def keep_recent(messages: list[ModelMessage]) -> list[ModelMessage]:
    # 마지막 10개만 유지 (최근 5턴 = Req-Res 페어 5쌍)
    return messages[-10:] if len(messages) > 10 else messages
```

### 이 함수가 하는 일

PydanticAI의 Agent가 **매 요청 직전에** 자동으로 호출하는 "히스토리 다듬기 함수". 현재 대화 히스토리를 받아서 **마지막 10개만 남기고 앞쪽은 잘라낸다**.

### 왜 10개인가 — "5턴"의 의미

LLM 대화에서 한 "턴"은 **사용자 메시지 1개 + AI 응답 1개 = 2개 메시지**다. 그래서 10개는 정확히 **5턴**에 해당한다.

| 메시지 # | role | 의미 |
|----------|------|------|
| 1 | user | 첫 번째 질문 |
| 2 | assistant | 첫 번째 답변 |
| 3 | user | 두 번째 질문 |
| 4 | assistant | 두 번째 답변 |
| ... | ... | ... |
| 9 | user | 다섯 번째 질문 |
| 10 | assistant | 다섯 번째 답변 |

11개째부터는 맨 앞을 잘라낸다. → **최근 5턴만 기억하는 챗봇**.

### 왜 히스토리를 잘라야 하나 — 토큰 비용

LLM API는 **토큰 단위로 과금**한다 (대략 단어 1개 ≈ 1.3토큰). 요청마다 전체 히스토리를 다 같이 보내기 때문에 대화가 길어질수록:
- 요청 토큰 수 ↑ → 비용 ↑
- 요청 토큰 수 ↑ → 응답 속도 ↓
- 컨텍스트 윈도우(최대 토큰 한도) 초과 시 에러

그래서 **오래된 대화는 잘라내는 것**이 일반적인 관행이다. 10개(5턴)는 "일반 CS 대화에서 문맥 유지에 충분하면서도 비용은 억제할 수 있는 타협점".

### `async` 함수인 이유

PydanticAI의 `history_processors`는 **비동기 함수를 요구한다**. 이 함수 자체는 async로 할 일이 없지만(단순 리스트 슬라이싱), 인터페이스 규격을 맞추려고 `async`로 선언했다.

### 삼항 연산자 해석

```python
return messages[-10:] if len(messages) > 10 else messages
```

- 메시지가 10개 초과 → 뒤쪽 10개만 슬라이싱해서 반환 (`messages[-10:]`)
- 10개 이하 → 원본 그대로 반환

`if len(messages) > 10` 체크 없이 그냥 `messages[-10:]`로만 해도 동작은 똑같다 (슬라이싱은 범위를 넘어도 에러 안 남). 명시적인 체크로 의도를 드러낸 스타일.

## Line 47-51: Agent 싱글톤 생성

```python
agent = Agent(
    GEMINI_MODEL,
    instructions=SYSTEM_PROMPT,
    history_processors=[keep_recent],
)
```

### PydanticAI Agent란

LLM 호출을 감싸는 고수준 클래스. 그냥 `requests.post("https://api.google.com/...", ...)` 같은 저수준 HTTP 호출이 아니라:
- 모델 이름만 주면 알아서 적절한 프로바이더(Google, OpenAI, Anthropic 등)의 API 클라이언트를 만들고
- 시스템 프롬프트, 히스토리, 사용자 메시지를 자동으로 표준 포맷으로 조립하고
- 응답을 구조화된 객체로 반환해준다.

→ LLM 통신의 **번거로운 부분을 다 알아서 해주는 래퍼**.

### 파라미터 3개 해설

#### `GEMINI_MODEL`

첫 번째 인자로 모델 이름을 넘긴다. `"google-gla:gemini-3.1-flash-lite-preview"` 같은 형식. PydanticAI가 이 문자열을 보고 "아, Google의 Generative Language API의 gemini-3.1-flash-lite-preview 모델이구나" 하고 해석한다. API 키는 `os.environ["GOOGLE_API_KEY"]`에서 자동으로 읽는다 (`config.py`에서 이미 로드됨).

#### `instructions=SYSTEM_PROMPT`

시스템 프롬프트 설정. PydanticAI는 `instructions`와 `system_prompt` 두 가지 방식을 제공하는데, **우리는 `instructions`를 쓴다**. 둘의 차이는 중요하다:

| 방식 | 동작 |
|------|------|
| `system_prompt="..."` | 첫 요청 시 `messages[0]`에 **저장**됨. 이후 히스토리에 포함되어 계속 전송됨. |
| `instructions="..."` | `messages`에 저장되지 **않고**, 매 요청 시 **별도 필드**로 API에 전달됨. |

**`instructions`를 쓰는 이유**:
- 히스토리에 시스템 프롬프트가 들어가지 **않음** → `keep_recent`가 잘라낼 일이 없음 (시스템 프롬프트가 "역사"의 일부가 아니라 "영구 규칙"으로 취급됨)
- 시스템 프롬프트는 항상 최신 버전이 쓰임 (`_sessions` 캐시에 저장된 건 사용자/AI 메시지만)
- 코드 배포 후 시스템 프롬프트를 바꾸면 **기존 세션에도 바로 적용**됨

→ 시스템 프롬프트를 "규칙"으로 보느냐 "역사"로 보느냐의 차이. 우리는 규칙이라 `instructions`가 맞다.

#### `history_processors=[keep_recent]`

위에서 정의한 `keep_recent` 함수를 **처리기 리스트**로 등록한다. Agent가 매 요청 직전에 이 리스트의 함수들을 순서대로 실행해서 히스토리를 다듬는다.

**중요 포인트**: 이건 함수를 **"등록"** 만 하는 것이지, 지금 당장 실행되는 게 아니다. 나중에 `agent.run(...)`이 호출될 때마다 PydanticAI가 내부적으로 `keep_recent(messages)`를 호출해서 결과를 쓴다.

리스트로 받는 이유는 여러 개를 등록할 수 있어서다 (예: `[keep_recent, summarize_old, filter_pii]`). 우리는 하나만 쓴다.

### 왜 모듈 레벨 전역 변수인가

`config.py`의 `embedder`와 같은 이유. `Agent(GEMINI_MODEL, ...)` 생성 시 내부적으로 HTTP 클라이언트가 초기화된다. 매 요청마다 새로 만들면:
- 초기화 비용 낭비
- 메모리 낭비
- API 연결 세팅 비용 중복

서버 시작 시 한 번만 만들어놓고 모든 요청이 **같은 Agent 객체를 공유**한다. → **모듈 레벨 싱글톤 패턴**.

## Line 53: 세션 캐시

```python
_sessions: TTLCache = TTLCache(maxsize=100, ttl=1800)
```

### TTLCache란

일반 딕셔너리 + **자동 만료 기능**. 항목을 넣으면 일정 시간 후 자동으로 삭제된다.

### 파라미터 해설

| 파라미터 | 값 | 의미 |
|----------|-----|------|
| `maxsize` | 100 | 최대 100개 세션까지 저장. 초과 시 가장 오래된 것부터 자동 삭제 (LRU) |
| `ttl` | 1800 | Time To Live. 초 단위. **30분(=1800초) 지나면 자동 삭제** |

→ "동시에 최대 100명의 사용자 세션을 30분간 기억"하는 캐시.

### 왜 이런 설정인가

**30분**: 사용자가 30분 동안 아무 메시지도 안 보내면 "대화 끊겼다"고 간주하고 히스토리를 버린다. 일반적인 CS 세션 기준.

**100개**: 동시에 100명이 대화 중이라고 가정. 동시 사용자 101명이 되면 가장 오래된 1명의 세션이 밀려난다. 이건 프로젝트 규모에 따라 조정해야 할 숫자 (운영 시 늘리거나 Redis로 교체).

### 왜 `_sessions`처럼 언더스코어로 시작하나

파이썬 관례로 **언더스코어로 시작하는 변수/함수는 "모듈 내부용"**이라는 표시다. 다른 파일에서 `from app.llm import _sessions`로 가져다 쓰지 말라는 시그널. 실제로 이 캐시는 `generate_response()` 내부에서만 사용된다.

### 왜 파일 DB나 Redis 안 쓰고 메모리 캐시?

- **장점**: 설정 0줄, 속도 최고, 외부 의존성 없음
- **단점**: 서버 재시작 시 모든 세션 증발, 멀티 인스턴스 환경에서 세션 공유 불가

현재는 단일 서버 MVP라 이걸로 충분. 스케일 아웃 시 Redis로 교체하면 됨. **"지금 필요한 만큼만"** 만드는 전형적인 YAGNI 스타일.

### 타입 힌트 `_sessions: TTLCache`

콜론 뒤 `TTLCache`는 **변수의 타입**을 명시한다. 안 써도 파이썬은 동작하지만 IDE 자동완성이나 타입 체커(`mypy`)가 이걸 보고 힌트를 준다. 실제 실행 시에는 무시됨 — 순수 문서화 역할.

## Line 56-73: `generate_response` — 핵심 함수

```python
async def generate_response(
    session_id: str | None,
    context_chunks: list[str],
    user_message: str,
) -> tuple[str, str]:
    sid = session_id or str(uuid.uuid4())
    stored_messages: list[ModelMessage] = list(_sessions.get(sid, []))

    if context_chunks:
        context_block = "\n\n---\n\n".join(context_chunks)
        content = f"[참고 문서]\n{context_block}\n\n[사용자 질문]\n{user_message}"
    else:
        content = f"[참고 문서]\n(관련 문서 없음)\n\n[사용자 질문]\n{user_message}"

    result = await agent.run(content, message_history=stored_messages)
    _sessions[sid] = result.all_messages()

    return sid, result.output
```

이 파일의 **유일한 public 함수**. `routers/chat.py`가 매 사용자 요청마다 이 함수를 호출한다. 한 줄씩 뜯어본다.

### Line 56-60: 함수 시그니처

```python
async def generate_response(
    session_id: str | None,
    context_chunks: list[str],
    user_message: str,
) -> tuple[str, str]:
```

- **`async`**: 내부에서 `await agent.run(...)`을 호출하니까 당연히 async. FastAPI가 async 함수를 기본으로 다룬다.
- **`session_id: str | None`**: 세션 ID. 첫 요청이면 `None`이 들어온다 (프론트에서 안 보내니까).
- **`context_chunks: list[str]`**: RAG가 찾아온 참고 문서들. `rag.py`가 `["텍스트1", "텍스트2", ...]` 형태로 반환한 값.
- **`user_message: str`**: 사용자 입력 원문.
- **`-> tuple[str, str]`**: 반환 타입. `(session_id, 응답_텍스트)` 두 개 묶음.

### Line 61: 세션 ID 결정

```python
sid = session_id or str(uuid.uuid4())
```

파이썬의 `or` 연산자를 **기본값 패턴**으로 활용.

- `session_id`가 `None`이나 빈 문자열이면 → 오른쪽이 평가됨 → `uuid.uuid4()` 호출 → 새 UUID 생성
- `session_id`가 뭔가 값이 있으면 → 그걸 그대로 사용

`uuid.uuid4()`는 `UUID` 객체를 반환하는데, `str(...)`로 감싸서 `"abc-123-..."` 같은 문자열로 바꿔야 딕셔너리 키로 쓰기 편하다.

→ **첫 요청이면 새 세션 시작, 이후 요청이면 기존 세션 이어감**.

### Line 62: 이전 히스토리 로드

```python
stored_messages: list[ModelMessage] = list(_sessions.get(sid, []))
```

한 줄에 여러 개념이 담겨있다. 뜯어본다.

#### `_sessions.get(sid, [])`

- 딕셔너리(`TTLCache`)에서 `sid` 키에 해당하는 값을 꺼냄
- **키가 없으면 빈 리스트 `[]`를 반환** (= 새 세션이거나 30분 지나서 만료됨)
- `_sessions[sid]`를 썼다면 키 없을 때 `KeyError`가 났을 것

#### `list(...)`로 감싸는 이유 — **복사본 생성**

중요한 포인트다. `_sessions.get(sid, [])`가 반환하는 리스트는 **캐시 안의 원본 객체의 참조**다. 그대로 쓰면 아래에서 Agent가 히스토리를 수정할 때 캐시 원본까지 바뀔 수 있다.

`list(...)`로 감싸면 **얕은 복사본**이 생긴다 (새로운 리스트 객체, 내용은 같음). 이러면 Agent가 이 리스트를 조작해도 캐시 원본은 안전하다.

→ **캐시 원본 보호**를 위한 방어적 복사 패턴.

#### `list[ModelMessage]` 타입 힌트

리스트 안에 `ModelMessage` 객체들이 들어있다는 표시. PydanticAI가 정의한 메시지 타입. 런타임에는 그냥 리스트일 뿐이지만, 타입 체커와 개발자에게 "이건 LLM 메시지 리스트다"라고 알려준다.

### Line 64-68: 프롬프트 조립

```python
if context_chunks:
    context_block = "\n\n---\n\n".join(context_chunks)
    content = f"[참고 문서]\n{context_block}\n\n[사용자 질문]\n{user_message}"
else:
    content = f"[참고 문서]\n(관련 문서 없음)\n\n[사용자 질문]\n{user_message}"
```

RAG 검색 결과를 LLM이 읽을 수 있는 프롬프트로 조립하는 부분.

#### 왜 두 가지 분기?

- **`context_chunks`에 뭔가 있으면** → 그 내용을 구분선으로 이어붙여서 포함
- **비어있으면** → "관련 문서 없음"이라고 명시

빈 리스트를 그냥 이어붙이면 `[참고 문서]\n\n\n[사용자 질문]` 같은 이상한 형태가 된다. LLM에게 "참고 문서가 없다"는 상태를 **명시적으로** 알려줘야 `SYSTEM_PROMPT`의 "정보 없으면 '확인 후 안내드리겠습니다' 답하라" 규칙이 제대로 발동된다.

#### `"\n\n---\n\n".join(context_chunks)`

`join()`은 리스트 요소 사이사이에 구분 문자를 끼워 하나의 문자열로 만드는 함수.

```python
["A", "B", "C"]
→ "A\n\n---\n\n B\n\n---\n\nC"
```

`---`는 마크다운 가로선 문법이지만 여기서는 **시각적 구분선** 역할만 한다. LLM이 "이 세 덩어리가 서로 다른 문서구나" 하고 인식할 수 있게 해주는 장치.

#### f-string으로 완성된 프롬프트 예시

```
[참고 문서]
발음 점수는 100점 만점으로, 정확도 40%, 유창성 30%...

---

발음 피드백 화면에서는 단어별 정확도를...

---

녹음 시 주의사항: 조용한 환경에서...

[사용자 질문]
발음 점수는 어떻게 매겨지나요?
```

이 문자열 하나가 **user 메시지로 LLM에게 전달**된다. 시스템 프롬프트(역할 지시)는 Agent 생성 시 `instructions=`로 이미 설정돼 있어서 여기서 또 쓸 필요 없음.

#### 왜 이 구조로 조립하나

LLM은 **구조화된 텍스트**를 잘 인식한다. `[참고 문서]`와 `[사용자 질문]`이라는 라벨로 경계를 명확히 하면:
- LLM이 "참고 문서는 근거, 사용자 질문은 답변해야 할 것"으로 확실히 구분
- 시스템 프롬프트에서도 `[참고 문서]에 제공된 내용을 기반으로 답변하세요`라고 이 라벨을 직접 참조
- → 라벨 이름이 **시스템 프롬프트와 user 메시지에서 일치해야** 연결이 자연스럽다

### Line 70: LLM 호출

```python
result = await agent.run(content, message_history=stored_messages)
```

이 한 줄이 **진짜 LLM API 호출**이 일어나는 곳.

#### `agent.run(...)`

PydanticAI의 Agent에게 "이 메시지로 LLM을 돌려줘"라고 부탁하는 메서드. 내부적으로 일어나는 일:

1. `stored_messages`를 `history_processors` 리스트의 함수들(우리는 `keep_recent` 하나)에 통과시켜 다듬음 → 10개 초과면 자름
2. `instructions` (시스템 프롬프트) + 다듬어진 히스토리 + 새 `content`(user 메시지)를 하나의 메시지 배열로 조립
3. HTTP 요청 바디를 만들어서 Gemini API로 POST
4. 응답을 파싱해서 `result` 객체로 반환

#### `await` 키워드

HTTP 요청은 수 초가 걸릴 수 있다. 그동안 서버가 다른 요청을 못 받으면 성능이 망가진다. `await`를 쓰면:
- "여기서 기다릴 게 있으니, 서버야 잠깐 다른 요청 처리해도 돼"
- Gemini 응답이 오면 이 지점부터 이어서 실행

→ FastAPI의 동시성 처리의 핵심. 이 함수가 `async`로 선언된 이유.

#### `result` 객체

`result`는 `AgentRunResult` 타입의 객체로, 주요 속성:
- `result.output` — LLM이 생성한 **답변 텍스트** (문자열)
- `result.all_messages()` — **시스템 + 이전 히스토리 + 새 user + 새 assistant 메시지**까지 모두 포함한 전체 대화 배열

### Line 71: 새 히스토리 저장

```python
_sessions[sid] = result.all_messages()
```

Agent가 돌려준 `all_messages()`를 세션 캐시에 덮어쓴다.

#### `all_messages()`에 뭐가 들어있나

이번 `agent.run()` 호출 전체에 관여한 메시지들을 전부 포함한다:
- 이번에 보낸 user 메시지 (방금 조립한 `content`)
- LLM이 생성한 assistant 응답

`instructions`는 **포함되지 않는다** (위에서 설명한 대로). 그래서 캐시에 쌓이는 건 순수 user/assistant 메시지만.

#### 다음 요청 시 어떻게 쓰이나

다음 사용자 요청이 같은 `session_id`로 들어오면:
1. Line 62에서 이 캐시를 다시 꺼내옴 → 이전 대화 N개 전부 로드
2. Line 70에서 `message_history`로 전달 → LLM이 "이전 대화 있었구나" 인식
3. `keep_recent`가 10개 넘으면 앞부분 잘라냄
4. LLM이 이전 맥락 고려해서 응답

→ 이 한 줄이 **챗봇이 기억력을 갖게 하는 핵심**. 안 쓰면 매 요청이 "처음 만난 대화"가 된다.

### Line 73: 반환

```python
return sid, result.output
```

튜플로 두 값을 반환:
- `sid` — 세션 ID (첫 요청이면 새로 만든 UUID, 아니면 받은 그대로). 호출자가 `ChatResponse.session_id`에 넣어서 프론트로 돌려줘야 함.
- `result.output` — LLM이 생성한 답변 텍스트.

`routers/chat.py`에서 이걸 받아 `ChatResponse`에 담아 그대로 클라이언트에게 반환한다.

| 개념 | 구현 방식 |
|------|----------|

## 핵심 정리

`llm.py`는 **"챗봇의 두뇌"** 다. 3가지 역할을 한다:

1. **정체성 부여** — `SYSTEM_PROMPT`로 "너는 Jarana의 CS 에이전트, 이런 규칙을 따라라" 지시
2. **기억력 부여** — `_sessions` TTLCache로 세션별 대화 유지, `keep_recent`로 5턴만 유지
3. **실제 LLM 호출** — `agent.run()`으로 Gemini에게 컨텍스트+질문 전달, 응답 수신

가장 기억해야 할 것 3가지:

1. **`instructions=` vs `system_prompt=` 의 차이** — 우리는 `instructions`를 써서 시스템 프롬프트가 히스토리에 저장되지 않게 했다. 덕분에 `keep_recent`가 시스템 프롬프트를 실수로 자를 일이 없고, 배포 후 프롬프트 변경이 기존 세션에도 즉시 반영된다.

2. **`history_processors`는 "등록"일 뿐, 실행은 `agent.run()` 내부에서 자동** — `keep_recent`는 여기서 정의만 해두고, 실제로는 PydanticAI가 매 요청 시 알아서 불러준다.

3. **`list(_sessions.get(sid, []))`의 방어적 복사** — 캐시 원본을 보호하기 위해 꼭 필요한 방어 코드. 복사 안 하면 Agent가 히스토리 수정 시 캐시가 오염될 수 있다.

이 파일만 이해하면 챗봇이 "어떻게 역할을 유지하고, 어떻게 기억하고, 어떻게 답변을 만들어내는지" 전부 설명할 수 있다.
